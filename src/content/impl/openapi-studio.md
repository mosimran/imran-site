<div class="memo"><b>How to read this note.</b> This is the reference design for an editor whose
document is a specification: what the constraint forces, the decisions that follow, and the
failure modes the shape has. It is a solution path for a system like the one built rather than
a disclosure of its internals. Schemas, deployment configuration, customer data and the product
roadmap are deliberately absent.
<br><br>This note reports no figures, and section 4 names the ones that would matter.</div>

## 1. The constraint

An API specification is somebody else's file and it has to come back unchanged.

That sentence does more work than it looks like. An editor for a standard format is not
handed a blank document. It is handed a file a team already depends on, generated by their
build, checked into their repository, consumed by their client generators, and reviewed in
pull requests by people who will read the diff. If the editor returns something semantically
equivalent but textually rearranged, the diff is unreadable and the tool is abandoned quietly.

So the internal model cannot be a convenient shape that happens to import and export. It has
to be **the specification itself**, including the parts the editor has no opinion about.

The second constraint arrives with the first. A spec is not one view. It is a tree of paths, a
flat list of endpoints, a rendered document, a set of forms, an executable set of requests, and
a set of tools an agent can call. Six audiences for one file. The naive build gives each of them
the model it wants.

## 2. The decision everything follows from

**One object. Every view is a pure function of it.**

**2.1. The model is the format, and the type system enforces it.** Every field maps to the
specification and nothing else is admitted. This is **enforced at the type boundary** rather
than by review: a view that wants somewhere to keep its collapsed branches cannot put it on the
document, because the document has no such field and adding one is a visible change to a shared
type that everything else compiles against.

**2.2. Views are derived, never stored.** Each surface is a function from the document to a
structure that surface understands. Nothing derived is persisted. A cached view is a second
model with a different name, and the first bug it produces is a canvas showing an endpoint the
table has already lost.

**2.3. Shared decomposition lives in one place.** Two surfaces need paths broken into a segment
tree, and the tempting version is to write it once and paste it. Pasted, they diverge on the
cases nobody tests, and then the sidebar and the canvas disagree about a path with a trailing
slash. One builder, both callers.

**2.4. References stay unresolved in the document.** Resolution is a separate utility called
when a consumer needs a flattened view. This makes every consumer harder and it is the only way
the author's file survives: a schema referenced in nine places must come back as one definition
and nine references, not nine copies.

**2.5. Editing writes the object, not the view.** A form binds to the document. It does not
patch the canvas and let the canvas inform the table. There is one write path and every surface
recomputes from it.

## 3. What this buys the person using it

The visible feature is that the views agree. The valuable one is that adding a view is cheap
and adding a view is what this kind of product does forever.

Every team wants a different lens on the same file. One wants the tree, one wants a table they
can sort, one wants documentation for a customer, one wants to fire a request and see the
response, and increasingly one wants an agent to hold the tools. Under a shared representation
each of those is a function against a model that already exists, written and tested without
touching the others. Under per-view models each one is a migration.

There is a commercial edge to it that is easy to miss. A tool that round-trips a specification
without rearranging it can be introduced into a repository that already has one, which is where
every real customer is. A tool that reformats on save has to be adopted at the start of a
project, and almost nobody is at the start of a project.

## 4. Figures

**This note reports none.** The four that would mean something are the proportion of the
specification the model actually round-trips without loss, measured against a corpus of real
files rather than fixtures; the number of view-disagreement defects found after the shared
representation compared with before; the cost in engineer-days of adding a new view; and the
share of adapter behaviour covered by tests that assert against the specification rather than
against the current output.

None of those are published, and the third is the one that would settle whether the
architecture paid for itself.

## 5. What I would do differently

**Write the round-trip test before the second view.** The property that matters is that a file
in equals a file out, and it is testable from the first day against real specifications
collected from public repositories. It tends to arrive late, after a customer reports that their
diff is unreadable, and by then the offending shortcut is load-bearing.

**Decide where view state lives on the first day the question is asked.** Failure 5.1 is fixed
by a rule, and rules that arrive after the fourth violation cost a refactor. The first request
for a UI field on the document is not a nuisance, it is the architecture asking whether it is
serious.

**Treat conformance as a test corpus rather than a type definition.** Failure 5.4 stays open
because a type that permits a field is not evidence that the field behaves. The version of this
I would build again keeps a directory of real specifications, including the ugly ones, and
fails the build when a round trip changes a byte.
